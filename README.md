# پلتفرم کلاس آنلاین موسیقی

مارکت‌پلیس آموزش خصوصی موسیقی به‌صورت آنلاین. هنرجو ساز و استاد را انتخاب می‌کند، جلسه رزرو می‌کند، کلاس زنده روی سرور جیتسی برگزار می‌شود، و چرخه‌ی تمرین بعد از کلاس ادامه پیدا می‌کند.

📐 **[سند معماری کامل](docs/architecture.md)** — مدل داده، جریان‌ها، فازبندی و تصمیم‌های باز.

## ساختار

```
apps/
  api/
    src/db/schema/  اسکیمای Drizzle، تقسیم‌شده بر اساس دامنه
    src/availability/
    src/payment/    درگاه، سفارش، دفتر کل
    src/notification/ پورت پیامک، قالب‌ها، یادآوری
    src/queue/      صف و جاب‌های پس‌زمینه (BullMQ)
    src/main.ts     پروسه‌ی API
    src/worker.ts   پروسه‌ی وُرکر — جدا از API
    drizzle/        مایگریشن‌های SQL
  web/              فرانت‌اند Next.js  (هنوز ساخته نشده)
packages/
  shared/           تایپ‌ها و منطق خالص، مشترک بین فرانت و بک
docs/
  architecture.md   سند طراحی
```

منطق دسترس‌پذیری عمداً در `packages/shared` نشسته و **هیچ وابستگی به دیتابیس یا فریم‌ورک ندارد**. ورودی داده‌ی ساده است و خروجی داده‌ی ساده، تا کامل و ارزان تست شود. `apps/api` فقط داده را می‌خواند و به آن می‌سپارد.

## راه‌اندازی

```bash
pnpm install
```

```bash
cp .env.example .env
```

```bash
pnpm dev:infra
```

```bash
pnpm db:migrate
```

پستگرس روی `5433` و ردیس روی `6380` بالا می‌آیند — عمداً غیرپیش‌فرض، تا با سرویس‌های نصب‌شده روی سیستم تداخل نکنند.

بالا آوردن API:

```bash
pnpm --filter @music/api dev
```

روی `http://localhost:4000/api` بالا می‌آید.

بالا آوردن وُرکر — **پروسه‌ی جدا، و بدون آن سیستم نیمه‌کار است**:

```bash
pnpm dev:worker
```

دو پروسه‌ی جدا چون بار و نحوه‌ی مقیاس‌دادنشان فرق دارد: از API چند نمونه بالا می‌آید ولی وُرکر یکی می‌ماند. اگر وُرکر داخل API می‌نشست، هر نمونه‌ی API جارو را جدا اجرا می‌کرد.

بدون وُرکر، رزروِ پرداخت‌نشده اسلات استاد را **تا ابد** نگه می‌دارد — قید `EXCLUDE` وضعیت `PENDING_PAYMENT` را اشغال‌کننده می‌شمارد. جلسه‌ی تمام‌شده هم هیچ‌وقت بسته نمی‌شود و کسی یادآوری نمی‌گیرد. برای همین `GET /api/health` تا وقتی ضربان تازه‌ای از وُرکر نبیند `degraded` گزارش می‌کند.

### جاروهای پس‌زمینه

هر سه هر دقیقه اجرا می‌شوند و هر کدام ضربان جدای خودش را دارد؛ سلامت وُرکر بدترینِ این سه است، تا خوابیدن یکی زیر کارکردن بقیه پنهان نماند.

| جارو | کار |
|---|---|
| `expire-holds` | آزاد کردن اسلاتِ رزروِ پرداخت‌نشده و ناموفق کردن سفارش کهنه |
| `close-sessions` | بستن جلسه‌ی تمام‌شده، تشخیص عدم حضور، بازپرداخت عدم حضور استاد |
| `send-reminders` | یادآوری پیامکی ۲۴ و ۱ ساعت پیش از جلسه، به هر دو طرف |

**چرا جارو و نه جاب تأخیردار:** جابِ گم‌شده یعنی جلسه‌ای که تا ابد باز می‌ماند یا یادآوری‌ای که هیچ‌وقت نمی‌رود، و هیچ‌کدام سر و صدا نمی‌کنند. جارو حقیقت را هر بار از دیتابیس می‌خواند، پس بعد از هر قطعی خودش را ترمیم می‌کند. جزئیات در سند معماری، بخش ۸.

**بستن جلسه** پانزده دقیقه پس از پایان انجام می‌شود (`NO_SHOW_GRACE_MINUTES`) و وضعیت را از روی `teacher_joined_at` و `student_joined_at` تعیین می‌کند: هر دو آمدند `COMPLETED`، فقط استاد `NO_SHOW_STUDENT` (جلسه می‌سوزد)، فقط هنرجو `NO_SHOW_TEACHER` (سطر منفی در دفتر کل + بررسی ادمین)، هیچ‌کس `NO_SHOW`.

**یادآوری دو بار فرستاده نمی‌شود**، حتی اگر جارو ده بار اجرا شود یا وُرکر ری‌استارت شود: هر یادآوری یک سطر در `notifications` است و ایندکس یکتای `(booking_id, user_id, type)` سطر دوم را در سطح دیتابیس رد می‌کند. سطر اول علامت `SENT` می‌خورد و بعد پیامک می‌رود — یعنی بدترین حالتِ مرگ پروسه، *نرسیدن* یک یادآوری است نه رسیدن دوتایی‌اش.

اندپوینت‌های محافظت‌شده توکن `Bearer` می‌خواهند. گارد احراز هویت **سراسری** است و مسیرهای عمومی باید صریحاً با `@Public()` معاف شوند — تا اندپوینت جدیدی که یادت برود محافظتش کنی، بی‌سر و صدا باز نماند.

> ⚠️ **فرستنده‌ی پیامک هنوز واقعی نیست.** در حالت توسعه کد ورود و یادآوری‌ها در کنسول چاپ می‌شوند و کد ورود در پاسخ هم به صورت `devCode` برمی‌گردد. در محیط تولید، نبودِ `SMS_API_KEY` باعث می‌شود برنامه عمداً بالا نیاید — تا کد ورود کاربران در لاگ سرور ننویسد.

> ⚠️ **درگاه پرداخت هم هنوز واقعی نیست.** بدون `PAYMENT_MERCHANT_ID` یک درگاه جعلی استفاده می‌شود که مستقیم به آدرس بازگشت ریدایرکت می‌کند و هر پرداختی را تأیید می‌کند — کل جریان بدون حساب پذیرندگی از سر تا ته اجرا می‌شود. در محیط تولید، نبودِ این متغیر جلوی بالا آمدن را می‌گیرد، چون درگاه جعلی یعنی هر کسی بدون پرداخت یک ریال رزرو را قطعی می‌کند. آداپتور زرین‌پال نوشته شده ولی روی حساب واقعی اجرا نشده؛ هشدارهای بالای `ZarinpalGateway` را پیش از اولین فروش بخوانید.

### جریان پرداخت

```
POST /api/payments/checkout   →  سفارش PENDING + آدرس درگاه
        ↓ کاربر به درگاه می‌رود
GET  /api/payments/callback   →  تأیید سرور به سرور با مبلغ سفارش
        ↓ در یک تراکنش
   سفارش PAID · رزروها CONFIRMED · ثبت‌نام ACTIVE · سطرهای درآمد در دفتر کل
        ↓
   ریدایرکت به  WEB_ORIGIN/payment/result?order=…&status=paid
```

قاعده‌ای که نباید شکسته شود: **پارامتر `Status` که درگاه به مرورگر می‌دهد در هیچ تصمیمی خوانده نمی‌شود.** آن آدرس عمومی است و هر کسی می‌تواند با `Status=OK` صدایش بزند. تنها منبع حقیقت، پاسخ سرورِ درگاه به درخواست تأییدِ ماست، و مبلغ مورد انتظار در همان درخواست فرستاده می‌شود تا دستکاری مبلغ هم بی‌اثر شود.

آدرس بازگشت (`PAYMENT_CALLBACK_URL`) باید به API اشاره کند نه به فرانت‌اند.

### اتاق کلاس

```
POST /api/bookings/:id/join
        ↓ بررسی: طرفِ رزرو؟ · وضعیت CONFIRMED یا IN_PROGRESS؟ · داخل بازه؟
   { domain, roomName, jwt, expiresAt, moderator, config }
        ↓ فرانت با همین‌ها IFrame را می‌سازد
        ↓ config عیناً به configOverwrite می‌رود  ← «حالت موسیقی»
POST /api/bookings/:id/attendance   { event: "JOINED" | "LEFT" }
```

بازه‌ی مجاز ورود از **۱۰ دقیقه پیش از شروع** تا **۱۵ دقیقه پس از پایان**
است. خارج از آن، API **توکن صادر نمی‌کند** — نه اینکه صادر کند و جیتسی
ردش کند. توکنِ ردشده در مرورگر فقط یک پیام انگلیسی مبهم نشان می‌دهد، ولی
اینجا می‌شود گفت «اتاق ۱۰ دقیقه‌ی دیگر باز می‌شود» و حتی `opensAt` را
برای شمارش معکوس برگرداند.

توکن به `room_id` گره خورده و `nbf`/`exp` آن دقیقاً دو لبه‌ی همین بازه‌اند،
پس نه لینکِ لو رفته به درد کسی می‌خورد و نه توکنِ امروز کلیدِ همیشگی آن
اتاق می‌شود.

> ⚠️ **`config` را نادیده نگیرید.** پردازش‌های پیش‌فرض صوتی جیتسی برای
> گفتار تنظیم‌اند و صدای ساز را تخریب می‌کنند. این پروفایل آن‌ها را خاموش
> می‌کند و استریو با بیت‌ریت بالاتر می‌گیرد. جزئیات و شواهدِ تست واقعی در
> سند معماری، بخش ۶.۳.
>
> نتیجه‌ی جانبی‌اش: **هدفون سیمی الزامی است**. بدون حذف اکو، بلندگوی باز
> فیدبک لوپ می‌سازد. این باید در آنبوردینگ و چک‌لیست پیش از کلاس گفته شود.

> ⚠️ **ثبت حضور از سمت کلاینت می‌آید و قابل دستکاری است.** زمان‌ها ساعت
> سرورند و فقط داخل بازه‌ی باز بودن اتاق پذیرفته می‌شوند، ولی کسی که اصلاً
> وارد اتاق نشده هم می‌تواند خودش را «حاضر» ثبت کند. برای گزارش عادی کافی
> است، برای رفع اختلاف مالی نه — تأیید متقابل با هوک سمت سرور جیتسی در
> فاز بعد.
>
> **از وقتی جاروی عدم حضور اضافه شده، این بدهی اثر مالی هم دارد:** استادی
> که غیبت کرده می‌تواند خودش را حاضر ثبت کند و جلسه را از
> `NO_SHOW_TEACHER` (بازپرداخت) به `NO_SHOW_STUDENT` (سوختن) ببرد. برای
> همین `NO_SHOW_TEACHER` علاوه بر بازپرداخت خودکار، در صف بررسی ادمین هم
> می‌ماند و پیش از تسویه‌ی ماهانه باید دیده شود.

اسلات‌ها به صورت `date` (شمسی‌نشده، `YYYY-MM-DD` میلادی) و `startMinute` (دقیقه از نیمه‌شب به وقت تهران) گرفته می‌شوند، نه ISO با منطقه‌ی زمانی. تبدیل به UTC فقط در یک جا انجام می‌شود تا منطق منطقه‌ی زمانی بین کلاینت و سرور تکرار نشود.

```bash
pnpm test
```

تست‌های `apps/api` یکپارچگی‌اند و به پستگرس واقعی نیاز دارند — قید `EXCLUDE` که جلوی رزرو دوتایی را می‌گیرد با هیچ ماکی قابل اثبات نیست. قبل از اجرا `pnpm dev:infra && pnpm db:migrate` لازم است.

```bash

```

```bash

```

```

```

## قواعد ثابت پروژه

- همه‌ی زمان‌ها در دیتابیس **UTC** هستند. تبدیل به تهران و تقویم شمسی فقط در لایه‌ی نمایش.
- ساعت‌های روز به صورت **دقیقه از نیمه‌شب** (۰ تا ۱۴۳۹) ذخیره می‌شوند، نه تایپ `time`.
- **روز هفته: شنبه = ۰** تا جمعه = ۶. عمداً با `Date.getDay()` جاوااسکریپت متفاوت است.
- مبالغ `BigInt` و واحدشان **ریال** است.
- **اسلات‌های آزاد ذخیره نمی‌شوند** — هر بار از روی قوانین و استثناها محاسبه می‌شوند.
- نام جدول‌ها و فیلدها انگلیسی؛ محتوای رو به کاربر فارسی.
- شمارشی‌ها در `packages/shared/src/enums.ts` و `apps/api/src/db/schema/enums.ts` باید همگام بمانند.
- شماره‌ی موبایل همیشه به صورت **E.164** (`+989121234567`) ذخیره می‌شود. ورودی کاربر — با ارقام فارسی، خط تیره، یا هر پیشوندی — پیش از هر کاری از `normalizePhone` رد می‌شود.
- **حساب پول هرگز از ممیز شناور رد نمی‌شود.** درصد کمیسیون از دیتابیس رشته می‌آید و در `splitCommission` به عدد صحیح تبدیل می‌شود. سهم استاد تفریق می‌شود نه اینکه جدا محاسبه شود، تا `gross = commission + net` همیشه برقرار بماند — قید `ledger_amounts_balance` دقیقاً همین را می‌خواهد.
- **دفتر کل فقط افزودنی است.** بازپرداخت یک سطر منفی است، نه ویرایش سطر درآمد. مجموع `net_amount` هر استاد بدون هیچ محاسبه‌ی جانبی، بدهی واقعی پلتفرم به اوست.
- **وضعیتی که درگاه به مرورگر می‌دهد باور نمی‌شود.** تأیید پرداخت فقط سرور به سرور و با ارسال مبلغ مورد انتظار انجام می‌شود.
