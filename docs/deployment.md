# راهنمای انتشار

این سند فرض می‌کند کد آماده است و می‌خواهی آن را روی سرور بیاوری. برای
«چرا این‌طور ساخته شده» به `architecture.md` برو؛ اینجا فقط ترتیب کارها
و چیزهایی است که اگر جا بیفتند، خرابی‌شان دیر و بدشکل دیده می‌شود.

---

## ۰. سه چیزی که کد نمی‌تواند برایت انجام دهد

قبل از هر چیز، این سه با پنل و حساب بیرونی درست می‌شوند و هیچ‌کدام
تستِ سبز ندارند:

۱. **الگوی لوکاپ کاوه‌نگار** برای کد ورود، و **خط خدماتی** برای یادآوری‌ها.
۲. **سیاست باکت**: CORS و خواندن عمومی.
۳. **واحد مبلغ حساب زرین‌پال** — ریال یا تومان. (`pnpm verify:payment`
   با هزار تومان معلومش می‌کند.)

هر سه در بخش‌های بعدی توضیح داده شده‌اند. اگر یکی جا بیفتد، برنامه بالا
می‌آید و سالم به نظر می‌رسد.

---

## ۱. متغیرهای محیطی

`.env.example` منبع کامل است و توضیح هر متغیر کنار خودش نوشته شده.
اینجا فقط چیزی می‌آید که مخصوص تولید است.

برنامه هنگام بالا آمدن محیط را می‌سنجد (`apps/api/src/config/env.ts`) و
اگر چیزی کم باشد **عمداً بالا نمی‌آید** و همه‌ی مشکلات را یک‌جا فهرست
می‌کند. پس لازم نیست این جدول را حفظ کنی؛ یک بار اجرا کن و پیام را بخوان.

### لازم در هر محیط

| متغیر | نکته |
|---|---|
| `DATABASE_URL` | پروتکل باید `postgres:` یا `postgresql:` باشد |
| `REDIS_URL` | `rediss:` هم پذیرفته است |
| `JWT_SECRET` | با `openssl rand -base64 48`. مقدار `.env.example` در تولید **رد می‌شود** |

### لازم فقط در تولید

| متغیر | اگر نباشد چه می‌شود |
|---|---|
| `SMS_API_KEY` | آداپتور کنسول انتخاب می‌شد و کد ورود همه در لاگ می‌نشست |
| `SMS_OTP_TEMPLATE` | نام الگوی لوکاپ؛ اشتباهش خطای ۴۲۴ |
| `SMS_SENDER` | اختیاری — خط فرستنده‌ی پیام آزاد |
| `PAYMENT_MERCHANT_ID` | درگاه جعلی هر پرداختی را تأیید می‌کند |
| `PAYMENT_CALLBACK_URL` | باید `https` و از بیرون در دسترس باشد |
| `WEB_ORIGIN` | باید `https` باشد؛ هم CORS و هم مقصد بازگشت پرداخت |
| `S3_ENDPOINT` `S3_BUCKET` `S3_ACCESS_KEY` `S3_SECRET_KEY` | ذخیره‌سازی حافظه‌ای با هر ری‌استارت فایل‌ها را می‌بازد |
| `JITSI_*` (پنج‌تا) | صدور توکن ورود به کلاس خطا می‌دهد |
| `JITSI_WEBHOOK_SECRET` | هوک حضور همه‌ی رویدادها را رد می‌کند و هیچ بازپرداخت عدم حضوری خودکار نمی‌شود (بخش ۱۰) |

⚠️ **API باید روی همان دامنه‌ی ثبت‌شده‌ی فرانت باشد** — مثلاً
`api.example.com` کنار `example.com`. توکن تازه‌سازی در کوکی
`SameSite=Lax` می‌رود و مرورگر آن را فقط روی درخواست‌های هم‌سایت
می‌فرستد. زیردامنه و پورت متفاوت مشکلی ندارند، ولی دامنه‌ی کاملاً
متفاوت یعنی تمدید نشست بی‌صدا شکست بخورد — که به شکل «کاربرها مدام
بیرون می‌افتند» دیده می‌شود، نه به شکل خطا.

✅ **این یکی حالا هنگام بوت گرفته می‌شود.** اعتبارسنجی محیط دامنه‌ی
ثبت‌شده‌ی `WEB_ORIGIN` را با دامنه‌ی `PAYMENT_CALLBACK_URL` (که روی خودِ
API است) مقایسه می‌کند و اگر یکی نبودند بالا نمی‌آید. تنها راه دیدنِ
این خرابی پیش از کاربر واقعی همین است: نشانه‌اش فقط بعد از انقضای توکن
پانزده‌دقیقه‌ای ظاهر می‌شود، یعنی نه در تست دستی بلافاصله پس از استقرار.

اگر آدرس بازگشت پرداخت عمداً روی دامنه‌ی دیگری است، دامنه‌ی واقعی API
را در `API_ORIGIN` بگذار تا مقایسه روی آن انجام شود.

`WEB_ORIGIN` و `PAYMENT_CALLBACK_URL` اگر به `localhost` اشاره کنند رد
می‌شوند. این حالت از نبودنشان بدتر است: برنامه بالا می‌آید و سالم به نظر
می‌رسد، ولی درگاه کاربر را به جایی می‌فرستد که وجود ندارد — و اولین باری
که کسی می‌فهمد، اولین فروش است، با پولی که گرفته شده و رزروی که قطعی
نشده.

### آنچه **نباید** در تولید باشد

`ALLOW_DEV_LOGIN_CODE=true` کد ورود را در پاسخ `POST /api/auth/otp/request`
برمی‌گرداند — یعنی ورود به هر حسابی، از جمله ادمین. اگر در تولید روشن
باشد، برنامه بالا نمی‌آید.

### فرانت‌اند

| متغیر | |
|---|---|
| `NEXT_PUBLIC_API_URL` | مثل `https://api.example.com/api` |
| `NEXT_PUBLIC_SITE_URL` | برای `sitemap.xml`، `robots.txt` و تگ‌های canonical |

⚠️ این دو در **زمان بیلد** داخل باندل می‌نشینند. عوض کردنشان بعد از بیلد
هیچ اثری ندارد؛ باید دوباره بیلد بگیری.

## ۲. ترتیب مایگریشن

```
pnpm db:migrate          # drizzle-kit migrate روی DATABASE_URL
pnpm db:seed:catalog     # فقط سازها — هیچ کاربری نمی‌سازد
```

`db:migrate` را **پیش از** بالا آوردن API اجرا کن. کد جدید روی اسکیمای
قدیمی کار نمی‌کند و شکستش به شکل خطای ستون ناموجود در وسط یک درخواست
کاربر دیده می‌شود.

`db:seed:catalog` بارها قابل اجراست و متن سازها را به‌روز می‌کند. لازم
است چون صفحات ساز در زمان بیلد فرانت ساخته می‌شوند و بدون داده، بیلد یک
سایت خالی تولید می‌کند.

⚠️ **`pnpm db:seed` را در تولید اجرا نکن.** دو استاد ساختگی و یک ادمین با
شماره‌ی نوشته‌شده در مخزن می‌سازد. خودش هم در تولید امتناع می‌کند، ولی
به آن تکیه نکن — بررسی‌اش روی `NODE_ENV` است.

### مایگریشن تازه

`drizzle-kit generate` برای ستون `NOT NULL` بک‌فیل نمی‌سازد و روی جدولی
که سطر دارد می‌شکند. مایگریشن ۰۰۰۵ به همین دلیل دستی ویرایش شد. هر
مایگریشن تازه را پیش از اجرا روی تولید با چشم بخوان.

---

## ۳. ادمین اول

هیچ ادمینی از پیش وجود ندارد. ترتیبش:

۱. با شماره‌ی واقعی خودت در سایت **وارد شو** تا حساب ساخته شود.
۲. روی سرور: `pnpm db:admin 09121234567`
۳. در فرانت خارج شو و دوباره وارد شو — نقش داخل توکن دسترسی است و
   توکن قدیمی هنوز `isAdmin: false` دارد.

`db:admin` کاربر **نمی‌سازد**؛ اگر نباشد خطا می‌دهد. عمدی است: یک شماره‌ی
اشتباهِ تایپی نباید به یک حساب ادمینِ بی‌صاحب تبدیل شود.

گرفتن دسترسی: `pnpm db:admin --revoke 09121234567`

## ۴. دو پروسه، نه یکی

```
pnpm --filter @music/api start          # API
pnpm --filter @music/api start:worker   # وُرکر — پروسه‌ی جدا
```

**وُرکر جداست و فراموش کردنش رایج‌ترین اشتباه استقرار است.** بدون آن
هیچ درخواستی خطا نمی‌دهد و سایت سالم به نظر می‌رسد، ولی:

- اسلات‌های رزروِ پرداخت‌نشده هرگز آزاد نمی‌شوند
- یادآوری جلسه فرستاده نمی‌شود
- جلسه‌های تمام‌شده بسته نمی‌شوند
- فایل‌های منقضی از باکت پاک نمی‌شوند
- تسویه‌ی ماهانه ساخته نمی‌شود

`GET /api/health` این را می‌گوید. بدون وُرکر، `status` می‌شود `degraded`
و `sweeps` نشان می‌دهد کدام جارو خوابیده:

```json
{
  "status": "degraded",
  "database": "ok",
  "redis": "ok",
  "worker": "never",
  "sweeps": { "expire-holds": "never", "send-reminders": "never" }
}
```

سه جارو آستانه‌ی ۵ دقیقه دارند و دو جاروی شبانه ۲۶ ساعت. پس بلافاصله
بعد از استقرار، جاروهای شبانه چند دقیقه `never` می‌مانند تا اولین اجرا
انجام شود — وُرکر هنگام بالا آمدن یک بار همه را اجرا می‌کند، پس این حالت
کوتاه است.

مانیتورینگ را روی `status != "ok"` بگذار، نه روی کد HTTP: این اندپوینت
حتی وقتی `degraded` است ۲۰۰ می‌دهد.

## ۵. باکت — کاری که فقط دستی انجام می‌شود

بعد از پر کردن چهار متغیر `S3_*`، **پیش از هر چیز دیگری**:

```
pnpm verify:storage
```

کل مسیر را در برابر باکت واقعی می‌آزماید — پیش‌پرواز CORS، آپلود
امضاشده، خواندن عمومی و حذف — و می‌گوید کدام‌یک از «کلید»، «منطقه»،
«شکل میزبان» یا «سیاست باکت» مقصر است. خودِ سرویس برای هر چهار حالت یک
پیام مبهم می‌دهد.

سه چیز در پنل باکت دستی است و هیچ کدی جایگزینشان نمی‌شود:

### ۵.۱ CORS

باکت باید `PUT` را از `WEB_ORIGIN` بپذیرد. فایل مستقیم از مرورگر به باکت
می‌رود و بدون این، مرورگر درخواست را **پیش از رسیدن به سرویس** رد می‌کند
— خطایی که هیچ ربطی به امضا ندارد ولی دقیقاً شبیه خطای امضا دیده می‌شود.

هدرهای لازم: `PUT` و `GET` مجاز، `content-type` در `AllowedHeaders`.

### ۵.۲ خواندن عمومی

کلیدها تصادفی و غیرقابل حدس‌اند و خواندنشان عمومی است. اگر باکت خصوصی
بماند، آپلود موفق می‌شود ولی پخش‌کننده‌ی صوت در صفحه‌ی جلسه فایل را
نمی‌گیرد.

### ۵.۳ شکل میزبان

`S3_PATH_STYLE` را حدس نزن. آروان و لیارا زیردامنه‌ای‌اند (`false`)، ولی
انتخاب اشتباه به `SignatureDoesNotMatch` تبدیل می‌شود نه ۴۰۴ — چون
میزبان جزء امضاست — و ساعت‌ها دنبال اشکالِ سالمِ امضا می‌فرستدت.
`verify:storage` هر دو شکل را می‌آزماید و می‌گوید کدام است.

## ۶. پیامک

`SMS_OTP_TEMPLATE` نام **الگوی تأییدشده** در پنل کاوه‌نگار است، نه متن
پیام. الگو باید یک پارامتر داشته باشد که کد در آن می‌نشیند:

```
کد ورود شما به [نام پلتفرم]: %token
```

کد ورود از `verify/lookup` می‌رود چون متن آزاد برای OTP در ایران عملاً
تحویل نمی‌شود.

⚠️ **یادآوری‌ها مسیر جدایی دارند.** متنشان پویاست و در الگو نمی‌نشیند،
پس از `sms/send` می‌روند که خط خدماتی تأییدشده می‌خواهد. یعنی حالتی
ممکن است که کد ورود سالم کار کند و یادآوری‌ها خطای ۴۲۶ بگیرند — نیمی از
سیستم خراب، بدون اینکه ورود کاربر مشکلی نشان دهد. جاروی یادآوری خطا را
روی سطر اعلان می‌نویسد و در لاگ می‌آورد، پس اولین بار که یادآوری‌ای
نرفت، لاگ را نگاه کن.

خطای ۴۱۸ یعنی اعتبار حساب تمام شده. پرتکرارترین خرابی تولید است و هیچ
ربطی به کد ندارد.

## ۷. درگاه پرداخت

قاعده‌ای که نباید بشکند: **تأیید همیشه سرور به سرور است و وضعیتِ
برگشته در URL مرورگر خوانده هم نمی‌شود.** `payments/callback` عمومی است و
هر کسی می‌تواند با `Status=OK` صدایش کند؛ امنیت از این می‌آید که تنها راه
قطعی شدن سفارش، تأیید موفقِ سرورِ زرین‌پال با مبلغ درست است.

### واحد مبلغ — این را حدس نزن

```
pnpm verify:payment
```

یک تراکنش واقعی با **هزار تومان** از سر تا ته می‌برد: درخواست پرداخت،
آدرسی که خودت در مرورگر باز می‌کنی، و تأیید سرور به سرور. آخرش صریح
می‌گوید واحد درست کدام است.

چرا لازم است: کد `-50` فقط در مرحله‌ی **تأیید** ظاهر می‌شود، یعنی بعد
از اینکه پول از حساب کاربر رفته. اگر حساب پذیرندگی روی تومان باشد و ما
ریال بفرستیم، **هر** پرداختی این کد را می‌گیرد و هیچ چیز دیگری نشانه‌ای
نمی‌دهد. بدون این اسکریپت، اولین باری که دیده می‌شود اولین فروش است.

نتیجه در `PAYMENT_AMOUNT_UNIT` می‌نشیند (`RIAL` یا `TOMAN`) و در تولید
**اجباری** است — تنها چیزی در کل پیکربندی که کد نمی‌تواند خودش بسنجدش،
پس نباید پیش‌فرضِ خاموش داشته باشد. عوض کردنش هیچ تغییر کدی نمی‌خواهد،
که مهم است: لحظه‌ای که می‌فهمی، هر پرداخت در جریان دارد شکست می‌خورد.

این حالتِ شکست عمداً پرسر و صداست — مبلغ اشتباه بی‌صدا ثبت نمی‌شود.

برای آزمایش بدون پول واقعی `PAYMENT_SANDBOX="true"` بگذار. ولی سندباکس
واحد مبلغِ **حساب واقعی** را نشان نمی‌دهد؛ برای آن جواب، تراکنش باید
واقعی باشد.

آداپتور بین «قطعاً ناموفق» و «نمی‌دانم» فرق می‌گذارد: اولی سفارش را
`FAILED` می‌کند و دومی `PENDING` می‌گذارد تا جاروی مهلت یا بررسی دستی
سراغش برود. اگر در لاگ «پاسخ زرین‌پال شناخته نشد» دیدی، یعنی کد خطایی
آمده که در فهرست نیست — سفارش دست‌نخورده مانده و باید دستی بررسی شود.

## ۸. فرانت‌اند

```
pnpm --filter @music/web build
node apps/web/.next/standalone/server.js
```

⚠️ `next.config` روی `output: standalone` است، پس **`next start` کار
نمی‌کند**. اگر با آن تست کنی چیزی می‌بینی که ربطی به تولید ندارد.

⚠️ **بیلد به API بالا نیاز دارد.** صفحات سئو در زمان بیلد `fetch` می‌کنند
و شکست fetch عمداً بیلد را می‌شکند — بهتر از منتشر شدن یک سایت خالی.
پس ترتیب کل استقرار این است:

```
۱. db:migrate
۲. db:seed:catalog
۳. API بالا بیاید
۴. وُرکر بالا بیاید
۵. بیلد فرانت‌اند
۶. فرانت‌اند بالا بیاید
```

بیلد fetchها را کش می‌کند، پس بعد از تغییر داده ممکن است نتیجه‌ی قدیمی
ببینی.

## ۹. بعد از استقرار

```
curl https://api.example.com/api/health
```

انتظار: `status: "ok"`، هر پنج جارو `ok` یا (تازه بعد از استقرار)
`never` برای شبانه‌ها.

بعد یک بار کل مسیر را دستی برو:

- [ ] ورود با شماره‌ی واقعی — کد پیامک می‌رسد؟
- [ ] پاسخ `otp/request` **نباید** `devCode` داشته باشد
- [ ] یک صفحه‌ی ساز و یک پروفایل استاد باز می‌شود
- [ ] یک پرداخت واقعی با کمترین مبلغ — سفارش `PAID` می‌شود و رزرو قطعی؟
- [ ] ورود به اتاق کلاس در پنجره‌ی مجاز
- [ ] بعد از همان ورود، `classroomHookLastEventAt` در health دیگر `null` نیست
- [ ] آپلود یک فایل در حلقه‌ی یادگیری و پخشش
- [ ] `/sitemap.xml` و `/robots.txt` دامنه‌ی درست دارند

## ۱۰. هوک حضور جیتسی

بدون این بخش، سیستم کار می‌کند و هیچ خطایی نمی‌دهد — فقط حضور در کلاس
همان چیزی می‌ماند که مرورگر گفته، و **هیچ بازپرداخت عدم حضوری خودکار
انجام نمی‌شود.** به‌جایش هر عدم حضور استاد به شکل پرونده‌ی
`ATTENDANCE_UNVERIFIED` روی میز ادمین می‌نشیند.

### چرا

از وقتی جاروی بستن جلسه بازپرداخت می‌نویسد، «حاضر بودم» یک ادعای مالی
است. استادی که غیبت کرده می‌تواند همان درخواستی را بفرستد که مرورگر
می‌فرستد و نتیجه را از «پول به هنرجو برگشت» به «جلسه سوخت» تغییر دهد.

سرور جیتسی این را می‌داند: با `ENABLE_GUESTS=0` هیچ‌کس بدون توکنی که
همین API امضا کرده وارد اتاق نمی‌شود، پس هویتِ داخل رویدادِ prosody
ادعای خودمان است که او اعتبارش را سنجیده.

### نصب

```
./scripts/install-jitsi-attendance-hook.sh
```

از ماشین توسعه اجرا می‌شود و با ssh کار را روی سرور انجام می‌دهد:
ماژول `event_sync_component` را **از خود ایمیج** برمی‌دارد (دسترسی
اینترنت آن سرور محدود است) و در `/prosody-plugins-custom` می‌گذارد،
کانفیگ کامپوننت را در `/config/conf.d/event-sync.cfg.lua` می‌نویسد و
prosody را ری‌استارت می‌کند.

`JITSI_WEBHOOK_SECRET` باید از قبل در `.env` باشد؛ همان مقدار در کانفیگ
prosody می‌نشیند و API با آن رویدادها را می‌سنجد. با
`openssl rand -base64 48` بسازید و **همان `JITSI_APP_SECRET` نگذارید**
— اعتبارسنجی محیط این را رد می‌کند.

⚠️ **ماژول در ایمیج هست ولی خودبه‌خود لود نمی‌شود.** در
`/prosody-plugins-contrib/event_sync/` است و prosody فقط
`mod_X.lua` یا `X/mod_X.lua` را پیدا می‌کند — نام پوشه `event_sync`
است و نام ماژول `event_sync_component`. برای همین کپی لازم است.

⚠️ **ولوم ناشناس.** اگر `/config` و `/prosody-plugins-custom` در
`compose.yaml` به مسیر میزبان بایند نشده باشند، داکر ولوم ناشناس
می‌سازد. `restart` و `up -d` حفظش می‌کنند ولی `--renew-anon-volumes` و
`down -v` پاکش می‌کنند — و آن روز، بدون هیچ خطایی، حضور دوباره
تأییدنشده می‌شود. اسکریپت وضعیت را گزارش می‌دهد؛ اگر ناشناس بود، در
compose بایندش کنید.

### تأیید

```
./scripts/install-jitsi-attendance-hook.sh --check
```

یک کلاس واقعی برگزار کنید و بعد:

```
curl -s https://api.example.com/api/health | grep classroomHookLastEventAt
```

`null` بودنش بعد از اولین کلاس یعنی ماژول لود نشده یا رویداد به API
نمی‌رسد. این مقدار عمداً روی `status` اثر ندارد: هوک فقط وقتی حرف
می‌زند که کلاسی برگزار شود و سکوتش در شب و روزهای خلوت طبیعی است.
هشداری که هر شب روشن شود، بعد از دو روز دیده نمی‌شود.

ترتیب عیب‌یابی، از محتمل‌ترین:

| نشانه | معنی |
|---|---|
| در لاگ prosody هیچ اشاره‌ای به `event_sync` نیست | ماژول لود نشده — کپی یا کانفیگ سر جایش نیست |
| لاگ prosody: `API Response code 401` | راز مشترک دو طرف یکی نیست |
| لاگ prosody: خطای TLS | گواهی API داخل کانتینر شناخته نمی‌شود |
| رویداد می‌رسد ولی `outcome: UNKNOWN_ROOM` | نام اتاق `room_id` رزرو نیست — یعنی اتاق از مسیر سایت باز نشده |
| در لاگ API: `بدون هویت رسید` | کسی بدون توکن وارد شده؛ `ENABLE_GUESTS` روی سرور را ببینید |

### بعدش چه فرقی می‌کند

در لاگ جاروی بستن جلسه، عدد آخر (`… جلسه به دلیل تأیید نشدن حضور بدون
اثر مالی ماند`) باید صفر شود. غیرصفر ماندنش بعد از نصب یعنی یا هوک
افتاده یا کسی حضور جعل کرده — و هر دو باید دیده شوند.

## ۱۱. بدهی‌های آگاهانه‌ای که با این استقرار می‌روند

اگر روزی کسی این سند را می‌خواند و می‌خواهد بداند چه چیزی هنوز باز است:

- **حضورِ جعل‌پذیر** — ✅ بسته شد. تصمیم مالی حالا فقط روی رویدادهای
  سرور جیتسی گرفته می‌شود (بخش ۱۰). گزارش کلاینت هنوز هست و هنوز
  جعل‌پذیر است، ولی دیگر پول جابه‌جا نمی‌کند: جلسه‌ی تأییدنشده به‌جای
  بازپرداخت خودکار به صف ادمین می‌رود. **تا وقتی ماژول prosody نصب
  نشده، همه‌ی جلسه‌ها تأییدنشده‌اند.**
- **سیاست `NO_SHOW`** — هنوز تعریف نهایی ندارد.
- **فایل یتیم** — چیزی که آپلود شد ولی به رکوردی وصل نشد در باکت می‌ماند؛
  جاروی پاک‌سازی از روی جدول کار می‌کند نه فهرست باکت.
- **خروجی مارک‌داون بلاگ پاک‌سازی نمی‌شود** — محتوا فقط از پنل ادمین
  می‌آید. اگر نوشتن به استاد مهمان باز شود، این تصمیم باید بازبینی شود.
